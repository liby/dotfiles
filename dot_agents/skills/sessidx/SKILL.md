`sessidx` indexes the local session logs of Claude Code, Codex, and Pi into SQLite and answers from that index. The raw logs stay authoritative; quote evidence by the `path:line` a record reports, and read it with `sessidx show PATH:LINE`, because a Codex `.jsonl` path may exist on disk only as a compressed `.jsonl.zst`. Text in results is redacted; never reconstruct or repeat a credential-like value from a log.

## Read the output contract

Every command writes JSON Lines to stdout: data records with a `type` field, then exactly one `end` record. Judge the result by `end`, not by the exit code alone:

- `end.complete=false` means a result limit, the page size, a deadline, an unavailable range, or a stale refresh cut coverage. An empty incomplete result is not evidence of absence.
- `end.refresh.missing_roots` lists each absent session directory as the `AGENT=PATH` that `--root` accepts. One that never held indexed sessions, such as an agent the user does not run or `~/.codex/archived_sessions` before any thread is archived, leaves the result complete; one that disappeared after indexing makes the refresh stale.
- `end.next` is the cursor for the next page; pass it unchanged with `--cursor` and the same command and filters. `search` pages cover the first 100 ranked sessions; past them `next` is null with `complete=false`, so narrow the query to reach the rest.
- `end.error` carries the failure and any recovery instruction. Exit codes: 0 data, 1 no data, 2 error.
- A `search`, `grep`, or `show` page stays within 24 KiB so that you see its `end`; never shorten the output yourself with `head`, `cut`, or a slice, which drops `end`. A `grep` or `show` record too large for a page carries `part`, a piece of the record's JSON text, instead of `record`, and its `cut` entry gives the whole text's `bytes` and the `kept` bytes shown from `offset`; `show` continues the same record through `next`, and the joined `part` values parse as the record. A `search` session's `cut` names each hit text it shortened by JSON Pointer `field`. Read a cut `search` or `grep` hit with `sessidx show REF --around 0`. A `grep` match can lie in the part that was cut.

Run an explicit index once, then retry, when:

- The error says the schema changed: run `sessidx index --full`.
- The error says the views changed, or `end.refresh` has a `continuation`, meaning the two-second refresh stopped before indexing everything, as on first use or after an upgrade: run `sessidx index`.
- A search error says the index needs compacting: run `sessidx index`.

A full history takes several minutes, longer than many agents' default shell timeout, so give the command a timeout of at least ten minutes or run it in the background and wait for it to exit. An interrupted run keeps what it committed: queries then report `complete=false` with a `continuation`, and `sessidx index` finishes the rest.

A `writer_busy` refresh means another process, such as a running `sessidx index`, held the index lock for the whole two-second refresh; the query still answers from committed data and reports `stale`. Overlapping queries wait for one another within that time instead.

## Find a session

1. Start with `sessidx search 'TERMS'` using the most distinctive words, identifiers, error text, or file names from the request, and add filters only when the request states them: `--agent claude|codex|pi` (repeatable), `--since`/`--until` (UTC dates or RFC 3339), `--cwd DIR` for a project, `--role`, `--session-kind main|subagent` for sessions started on their own or spawned by another session (`unknown` when the log carries no evidence either way), `--session ID|PATH`. Session selectors (`--session` and a `show` target) match a whole ID, path, or link, never an ID prefix; one that matches nothing fails and names it. Terms are ANDed; keep a phrase's word order with double quotes inside the shell argument, as in `sessidx search '"connection refused"'`; Chinese text matches as a phrase.
2. Each `session` record is one session (one transcript file, with its `session_kind`, `parent_id`, `cwd`, and `started_at`) and up to three best hits. Open the evidence with `sessidx show REF` using a hit's `ref` (it includes 3 source lines on each side; `--around N` changes that), or read the whole session, a page at a time, with `sessidx show SESSION_ID_OR_LINK`. Each `record` is one source line as a redacted JSON object in `record`, shown once per role on that line; a hit is only the best match, so read around it before quoting. A Claude subagent is its own session, keyed by its agent ID, and its ID can repeat under another parent: when an ID names more than one transcript, `show` and `--session` fail and list their paths, so pass the path.
3. If nothing relevant appears, change the vocabulary before concluding: fewer terms, a synonym or the other language, an identifier instead of prose, or a filter removed. Search covers messages, tool inputs, and the first 2 KiB of tool outputs.
4. For exact strings or regexes deeper in tool outputs, or every occurrence rather than the best sessions, use `sessidx grep 'REGEX'` (case-insensitive with `(?i)`; there is no `-i`) with at least one narrowing filter (`--session`, `--cwd`, `--since`/`--until`, or `--agent`). Narrow until `end.complete` is true before reporting that something is absent, and report absence only for the scope that completed.

The current conversation can be indexed too. Exclude it only by a session ID or path you know is yours; recency, directory, and matching text do not identify it, because an older session or a subagent can repeat the request. Report the session's agent, ID, path, and the `path:line` evidence you read, and say when the answer rests on an incomplete search.

## Count behavior

Use `sessidx count commands|failures|denials|usage|compactions` instead of tallying search hits, which are ranked and deduplicated per session. Pass `--by` once, with a comma-separated subset of `agent,model,role,week,session_kind`, or with no value for one total row; `--program NAME` selects shell commands by program; shared filters narrow the window. `usage` and `compactions` have no role or program, so they refuse `--by role`, `--role`, and `--program`. Each row names its population, the parts inside it, and any count outside it; report the population and its unknown part with any rate:

- `commands`: `sites` that parsed, of which `sites_without_program` have no literal program or one that redaction withheld, and with `--program` `matching_sites`. Sites are static syntax, not executions. `unparsed_calls` are shell calls outside `sites` because their syntax did not parse.
- `failures`: `calls` = `failed` + `succeeded` + `outcome_unknown`. A call whose results carry neither failure nor success evidence has an unknown outcome rather than a successful one; a Codex `exec` wrapper's completion alone is not evidence that the commands inside it succeeded. With unknown outcomes, the failure rate `failed / calls` is a lower bound.
- `denials`: `results`, of which `denied` carry denial evidence, of which `denied_reason_unknown` have no known reason.
- With `--program`, `calls` or `results` hold only those that name the program, and `calls_with_unresolved_program` or `results_with_unresolved_program` count the others whose program is unknown and might be it.
- `usage`: `requests`, each counted once under its own model, and `passes`, each under the model that ran it, so an advisor's model can show passes and tokens with zero requests. Token sums add up over passes: `input` excludes cached and cache-written tokens, so the prompt is `input` + `cache_read` + `cache_write`, and `reasoning` is part of `output`. An optional field's sum covers only its `*_recorded` passes, so compare a sum with its recorded count, not with `passes`. Codex threads from builds that wrote no per-request record also count running totals they copied from their parent, so a fork's requests can repeat its parent's. Calls with no request record of their own, such as one that writes a compaction's summary, are not counted.
- `compactions`: `compactions` = `auto` + `manual` + `trigger_unknown`; `pre_tokens` and `post_tokens` sum the context sizes that `pre_tokens_recorded` and `post_tokens_recorded` compactions state. `model` is the session's model at the compaction, not one the compaction record names.

For a question the verbs cannot express, `sessidx sql 'SELECT ...'` runs one read-only query without refreshing, so its `end.refresh` holds only `stale` and `writer_busy`. Each result row is a `{"type":"row","data":{...}}` record, so read columns from `.data`. It fails rather than truncating above 10,000 rows or two seconds, and its output is not paged, so aggregate in SQL, narrow by time or session, and select `substr(text, 1, N)` rather than whole long text.

Query `sessions`, `events`, `canonical_events` (events without copied history, which counts use; a Claude message written as several records carries all their text on one row), `call_outcomes` (one row per canonical tool call with its outcome `ok`: 0, 1, or NULL when unknown), `commands`, `denials`, `requests` (one row per model request with its `path`, `line_no`, `ts`, `model`, token columns, `stop_reason` in the agent's own words, and `route`, the evidence named by `route_source` of where the agent sent it, which is not proof of how it was billed), `request_passes` (one row per pass of a request, joined by `request_id` to `requests.id`, with its `kind`, `model`, and its request's `route`), `request_errors` (one row per record that states a model request failed, with its `source`, `model`, `status`, `code`, and `route`; these are reports, not a part of `requests`, so never divide them by `requests` for an error rate), and `compactions` (one row per compaction with its `trigger`, `pre_tokens`/`post_tokens`, for Codex the `request_id` of the request that wrote it, and for Pi the `summary_*` usage of writing its summary, outside `count usage`); the other tables are index storage. `sessions` has one row per transcript with its `file_id`, `agent`, `session_id`, `parent_id`, `session_kind`, `path`, `cwd`, `started_at`, and its earliest and latest event times `min_ts` and `max_ts`, so list sessions there rather than by ranking them. `events` carries each event's `id`, `file_id`, `agent`, `session_id`, `path`, `line_no`, `ts` (UTC), `role`, `kind`, `model`, `tool`, and `canonical` (1 for the first copy, which counts use), and reads `text` only when a query names it; join `commands.event_id` or `denials.event_id` to `events.id`. For per-transcript correlation with `sessions`, use `e.file_id = s.file_id` or the indexed `e.path = s.path`; `(agent, session_id)` can name several transcripts and combines their events. `denials` carries one row per recognized denial: `source` names the channel (`hook`, `batch_hook`, `guard`, `marker`, `native_denial`, `permission_rule`, `user_rejected`, `classifier`, `classifier_unavailable`); `class` is `policy`, `coverage`, `error`, or `unknown`; `producer` is the producer a reason marker names, or NULL when no marker declared one or redaction withheld it; `reason_id` names the rule by the producer's own ID from a marker, or for frozen legacy wording by agent-guard's public ID (the earlier dotfiles guards' name for a rule only they had), with `unknown` for unmapped text, sentences shared by several kinds, and withheld markers, and historical wordings of the same rule sharing an ID. A row with NULL `producer` and a known `reason_id` was inferred from the frozen wording of agent-guard or the earlier dotfiles guards, so a query spanning logs before and after markers includes those rows explicitly, as in `producer = 'agent-guard' OR (producer IS NULL AND reason_id <> 'unknown')`, which leaves out the shared sentences. List a relation's columns with `sessidx sql "SELECT name FROM pragma_table_info('events')"`.

`sessidx doctor` reports parse errors and the unknown part of each stored population when a count looks implausible.
