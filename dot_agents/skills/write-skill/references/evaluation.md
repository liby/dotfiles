# Evaluation Protocol

1. Freeze the exact baseline bytes, runtime-visible catalog, sanitized cases, and expected observations before inspecting candidate output. Cases used to diagnose or author the change are regression cases, not held-out acceptance evidence.
2. Define discriminating checks. For routing, cover obvious triggers, paraphrases, near misses, and separate explicit `/name` and `$name` controls; use 8-10 positive and 8-10 negative cases for important skills. For global behavior, cover representative targets, adjacent no-change cases, and proportionality in every intended runtime.
3. Run baseline and candidate against the same inputs and runtime. For a new capability compare with and without the skill; for an existing capability compare the frozen old version with the candidate. Run nondeterministic routing boundaries repeatedly when the decision depends on trigger rate.
4. Record task outcome first. Add loaded files, selected versus invoked state, tokens, time, or tool calls only when they test the claimed benefit or explain a regression. Count `invoked` only when the full `SKILL.md` loads; label classifier-only output `selected`. A reference split succeeds only when common cases skip it and branch cases load it before the constrained action.
5. Assertions that pass in both configurations are regression controls, not evidence of skill value; assertions that fail in both do not support the candidate. For subjective output, use human review or a blind comparator without revealing which version produced each result.
6. Keep a validation split hidden and try fresh prompts before accepting an important rewrite. Retain the candidate only when the target behavior improves with no paired regression. If a branch misses a linked file, sharpen its load condition; revert the split when reliable discovery costs more than the context it saves.
