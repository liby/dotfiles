# Evaluation Protocol

1. Freeze the exact baseline bytes, runtime-visible catalog, sanitized cases, which of them exercise the changed text, and expected observations before inspecting candidate output. Derive expected observations from the target behavior, not from the candidate's wording, which would reward echoing it. Strip annotations that state or hint at the expected observation, such as a note that a built-in tool already answers the request. A task prompt that asks for or invites the scored behavior, as an explicit `/name` control does, measures prompt compliance: keep such a case as a control that catches a candidate breaking that behavior, but never count its pass as evidence that the instruction causes it. Cases used to diagnose or author the change are regression cases, not held-out acceptance evidence; for an important rewrite, also set aside a validation split that stays hidden while you write it.
2. Define discriminating checks. For routing, cover obvious triggers, paraphrases, near misses, and separate explicit `/name` and `$name` controls; use 8-10 positive and 8-10 negative cases for important skills. Every implicit-routing positive case, obvious triggers included, must be substantive enough to benefit from the skill: a runtime may answer a simple one-step request with basic tools even when the description matches, so a miss on one that basic tools still answer acceptably does not show a routing defect. For global behavior, cover representative targets, adjacent no-change cases, and proportionality. When the failure appeared only inside a longer flow, such as late in a session or after earlier steps, build cases that run that flow with the instructions it loads: a single-prompt case can pass in both arms while the same behavior still fails there.
3. Run baseline and candidate on the same inputs in each runtime the instruction targets. Cheaper models or effort can screen for failures, but confirm a failure, and base acceptance, on the models and effort the instruction runs under. A runtime too costly to run in full, or a later round that reruns only part of the suite, needs both arms on at least every case frozen as exercising the changed text and every case whose arms have differed on any runtime. For a new capability compare with and without the skill; for an existing capability compare the frozen old version with the candidate. Run nondeterministic routing boundaries repeatedly when the decision depends on trigger rate. Cap candidate variants and revision rounds before the first comparison; when variants of an addition or rewrite keep tying the baseline within run-to-run variation, stop generating more and report `no effect detected`, leaving step 7 to decide whether the text stays.
4. Keep the real model, harness, and skill discovery and loading in every trial, and isolate the real state the behavior under test does not need: writes stay in the trial's own workspace, temp space, and runtime session state, with the user's settings blocked even inside that state tree; network reaches only the model and the read-only services the cases need; the trial cannot drive other apps, local services, or unrelated processes; and the trial cannot read the evaluation itself: its scripts, cases, labels, the operator's session, and any session or history record that mentions them; for cases taken from real history, also the records that hold the case's own prompt, which show what followed it. Keep a history search the runtime relies on working over the remaining records rather than denying its whole store, which would make every lookup fail. Freeze this hidden set with the cases, so every trial of a comparison runs under the same condition. Replace a tool that could act on the user's browser, accounts, messages, or services with a stub that keeps its description, schema, responses, and error semantics, so routing faces the same choice. Enforce the boundary outside the agent, because runtime sandboxes and approval reviewers leave MCP servers, hooks, and approved escalations uncovered, and an outer boundary can keep an inner sandbox from applying. Before the first trial, attempt each block both directly and through one agent-driven run per runtime, checking every hidden class separately next to a readable control, because one rule covering several patterns can silently enforce only some of them, and confirm that the isolated runtime lists the same tools and skills as an unisolated one; a temp directory, a file sandbox, or lower concurrency is not that evidence. When a run turns out to have reached real state or read hidden material, stop the affected runs and keep their logs; before resuming, establish what changed from the affected service's own records, and rerun every trial whose tool calls touched what was readable.
5. Record task outcome first. Keep body loading, rule execution, and the final result as separate observations: a loading rate shows that the body arrived, not that its rules were followed or that the outcome improved. Add loaded files, selected versus invoked state, tokens, time, or tool calls only when they test the claimed benefit or explain a regression. Count `invoked` only when tool results have returned the evaluated version's complete `SKILL.md` body, in one result or across several, before the action the instruction constrains; a load request, a command start, the path in a command, or a partial read such as a range of its first lines shows only `selected`, so keep the run going until the rest of the body or a deciding action arrives. Classify a run that ends in a runtime error as a terminal failure rather than a routing outcome, and do not treat retry or reconnect events as terminal. Exclude a trial that saw the evaluation or its case's own real history, rerun it under the frozen condition, keep each original verdict, the reason for excluding or rerunning it, and the link to its rerun, and compare arms only under the same corrected conditions.
6. Assertions that pass in both configurations are regression controls, not evidence of skill value; assertions that fail in both do not support the candidate. Before reading the totals as a gain, a tie, or a regression, read the outputs of every case whose arms differ: offsetting wins and losses can sum to a tie that hides a paired regression, and the outputs show whether a difference comes from the instruction, the label, or noise. For subjective output, use human review or a blind comparator without revealing which version produced each result. When a target runtime at its deployed settings consistently contradicts an expected observation in both arms, re-check that observation against the full instruction before counting a failure; labelers who worked from the same brief share its omissions.
7. Isolation probes, detector replays, validators, and single-runtime smoke runs are local checks: they gate trials but are not acceptance evidence. Accept an addition or rewrite only when the target behavior improves beyond run-to-run variation with no paired regression, and an important rewrite only after it also passes the hidden validation split and fresh prompts. When the baseline passes every case you can build for an addition, flow cases included, those cases cannot show its value: keep it when it encodes a convention the user settled or a reproduced failure that no other owner covers and causes no regression, and drop it otherwise. Accept a removal or compression when the cases that exercise the changed text show no regression and, when the text encodes a convention the user settled or a reproduced failure, the changed text or an owner loaded before the action it constrains still carries it; judge text that no case can exercise by whether it earns its place under the test that opens `SKILL.md`.
8. A reference split succeeds only when common cases skip it and branch cases load it before the constrained action. If a branch misses a linked file, sharpen its load condition; revert the split when reliable discovery costs more than the context it saves.
