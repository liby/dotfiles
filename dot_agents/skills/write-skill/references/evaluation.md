# Evaluation Protocol

1. Freeze the exact baseline bytes, runtime-visible catalog, sanitized cases, and expected observations before inspecting candidate output. Derive expected observations from the target behavior, not from the candidate's wording, which would reward echoing it. Cases used to diagnose or author the change are regression cases, not held-out acceptance evidence.
2. Define discriminating checks. For routing, cover obvious triggers, paraphrases, near misses, and separate explicit `/name` and `$name` controls; use 8-10 positive and 8-10 negative cases for important skills. Every implicit-routing positive case, obvious triggers included, must be substantive enough to benefit from the skill: a runtime may answer a simple one-step request with basic tools even when the description matches, so a miss on one that basic tools still answer acceptably does not show a routing defect. For global behavior, cover representative targets, adjacent no-change cases, and proportionality in every intended runtime.
3. Run baseline and candidate against the same inputs and runtime. For a new capability compare with and without the skill; for an existing capability compare the frozen old version with the candidate. Run nondeterministic routing boundaries repeatedly when the decision depends on trigger rate. Cap candidate variants and revision rounds before the first comparison; when variants of an addition or rewrite keep tying the baseline within run-to-run variation, stop generating more and report `no effect detected`, leaving step 6 to decide whether the text stays.
4. Record task outcome first. Add loaded files, selected versus invoked state, tokens, time, or tool calls only when they test the claimed benefit or explain a regression. Count `invoked` only when the full `SKILL.md` loads; label classifier-only output `selected`. A reference split succeeds only when common cases skip it and branch cases load it before the constrained action.
5. Assertions that pass in both configurations are regression controls, not evidence of skill value; assertions that fail in both do not support the candidate. For subjective output, use human review or a blind comparator without revealing which version produced each result.
6. Keep a validation split hidden and try fresh prompts before accepting an important rewrite. Accept an addition or rewrite only when the target behavior improves beyond run-to-run variation with no paired regression. When the baseline already passes every case you can build for an addition, as with a step agents skip only late in long sessions, those cases cannot show its value: keep it when it encodes a convention the user settled or a reproduced failure that no other owner covers and causes no regression, and drop it otherwise. Accept a removal or compression when the cases that exercise the changed text, named before the run, show no regression and every such convention or failure the text encodes is still carried, by the changed text or by an owner loaded before the action it constrains; judge text that no case can exercise by whether omitting it can cause a concrete wrong action. If a branch misses a linked file, sharpen its load condition; revert the split when reliable discovery costs more than the context it saves.
