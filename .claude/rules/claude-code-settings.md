# Claude Code settings

This is not a settings reference. Keep only repository-specific decisions that cannot be recovered from the managed configuration, its owning code, or the [environment variable](https://code.claude.com/docs/en/env-vars), [settings](https://code.claude.com/docs/en/settings), and [sandbox](https://code.claude.com/docs/en/sandboxing) references.

Revalidate runtime-dependent evidence after upgrades.

## Ownership

Keep `~/.claude/settings.json` and `~/.claude.json` partially managed per the [configuration ownership boundary](../../.github/CONCEPTS.md#configuration-ownership), so keys source does not declare, which Claude Code writes at runtime, survive chezmoi applies. Do not replace their modifiers with complete templates; `chezmoi re-add` cannot reconcile these targets.

Each top-level key in `~/.claude/settings.json` has one of three roles:

- Managed: declared in `.chezmoitemplates/claude/settings.json`. Every apply overwrites the live value, so a change made inside Claude Code lasts only until the next apply. This is the default for any key source sets.
- Seed: declared in `$seeds` in `dot_claude/modify_private_settings.json`. Apply writes it only when the key is missing from the live file, and never touches it afterwards.
- Undeclared: in neither. Apply leaves the live value as Claude Code wrote it. Removing a key from the fragment moves it here without deleting its live value.

Seed a key only when routine use changes it so often that restoring it on every apply would undo that use. Only `model` and `effortLevel`, switched through `/model` and `/effort`, meet that bar; the seed still gives a new machine the intended starting value, which leaving them undeclared would not. Seed `model` as the `opus` alias rather than a model ID: a seed is written once, so an ID would freeze each machine on the generation current at its first apply, while the alias follows the Opus pin. Being changeable inside Claude Code is not the criterion: many managed keys, such as `advisorModel`, change in a session and stay managed, so make the change durable in the fragment. Keep `CLAUDE_CODE_EFFORT_LEVEL` unset because it overrides both `/effort` and the persisted `effortLevel`, which defeats the seed.

`~/.claude.json` has no seeds. `modify_dot_claude.json` overlays its declared keys and replaces each source-declared MCP server whole, so removed transport fields disappear; undeclared servers and all other state stay intact.

## Session retention and unattended runs

- `cleanupPeriodDays=99999` intentionally retains transcripts for a practically indefinite period.
- `CLAUDE_CODE_RETRY_WATCHDOG=1` keeps unattended sessions waiting through retryable capacity errors. Keep `fallbackModel` unset while the watchdog is on: the watchdog exists to wait for the requested model, while a fallback would silently downgrade the runs it protects.

## Privacy and feature delivery

`DISABLE_TELEMETRY=1` also disables the client that evaluates server-side feature flags, and first-party event logging shares that gate, so no setting keeps flags while dropping events. Every gated feature therefore stays at its default, and each one wanted here needs its own explicit opt-in. Leave `CLAUDE_CODE_GB_DISK_CACHE_WHEN_TELEMETRY_OFF` unset: it only makes an existing flag cache in `~/.claude.json` readable while telemetry is off, and only sessions where the flag client runs write that cache, so on a machine that always has telemetry off it has nothing to read.

`syncClaudeAiSkills=false` and `syncClaudeAiPlugins=false` guard against a session that re-enables flag evaluation: account sync is switched on server-side by flags, and with them the flag would pull claude.ai skills into context and the repository-managed registry would stop being the only source. One of the gated features is the built-in `agents-md` mod that reads `AGENTS.md` directly, which is why `.claude/CLAUDE.md` keeps its `@../AGENTS.md` import: gateway sessions cannot reach the mod at all.

Both fork mode and agent teams are intentionally enabled here: `CLAUDE_CODE_FORK_SUBAGENT=1` extends fork mode, already on by default in interactive sessions, to `claude -p` and the Agent SDK, and `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` turns on agent teams, which are off by default. Keep `CLAUDE_CODE_ENABLE_EXPERIMENTAL_ADVISOR_TOOL=1` as the advisor's first-party opt-in: it bypasses the `tengu_sage_compass2` feature flag that `DISABLE_TELEMETRY=1` stops fetching, and relaxes the client-side advisor model-pairing check to the API. Gateway sessions run as the Vertex provider and cannot use the advisor at all.

Do not consolidate the separate privacy controls into `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`; it would also disable automatic updates.

## Permission rules

Claude Code resolves an action against `permissions` rules before the auto-mode classifier sees it: a deny match blocks first, and an allow match skips classifier review, with documented exceptions such as writes to protected paths, commands that carry per-command allowed domains, and shell commands in a session with `autoMode.classifyAllShell`. `sandbox.excludedCommands` decides only where a command runs, not whether it may run, so an excluded command without an allow rule still goes to the classifier; do not mirror one list into the other.

- `Read`, `Edit`, and `Write` stay broadly allowed for routine file work, so their path deny rules are the file-tool boundary. The shared [agent guard](../../.github/CONCEPTS.md#agent-guard) runs for `Bash` and for `Read|Edit|Write|Grep`; its credential list lives in the external package, so review package coverage before adding a `Read` deny path here. `~/.ssh` is the exception: the guard allows public keys, client config, `allowed_signers`, and `known_hosts` inside an otherwise private directory, which a deny glob cannot express, so do not add `~/.ssh` deny rules back. Grep permits explicit public files; directory searches covering private SSH material must be narrowed. Do not use glob rewriting to grant access: composing public reinclusions with the caller's filter changes search scope.
- Keep bare `Bash` out of `permissions.allow`: auto mode suspends it, and in every other mode it approves any shell command.
- `Bash(herdr:*)` and `Bash(oracle:*)` stay globally allowed because their panes or sessions can continue after the invoking Skill's turn, when frontmatter preapproval no longer applies. `Bash(snow:*)` stays globally allowed for the standing direct-command and native-SSO execution path owned by [Shared agent execution](../../.github/CONCEPTS.md#shared-agent-execution). Their sandbox exclusions remain separately necessary for Herdr control, Oracle browser control, and native Snowflake SSO.
- `Bash(codex:*)` and `Bash(pi:*)` stay globally allowed by explicit user decision: agents choose their own flags for each consultant run, such as an approval-disabling `-c 'approval_policy="never"'` that the managed Codex defaults do not need, and the classifier denies such a run as `Create Unsafe Agents` from the command text alone. A global instruction against each flag would not cover the next one, so the rules skip classifier review for these commands, including `codex`, which also runs outside the sandbox.
- Other host CLIs get no global allow rule. Git and other same-turn commands keep their narrower Skill grants unless a current-version reproducer shows Claude denying the matching grant, and `chezmoi` and `docker` stay on the classifier path although they are sandbox-excluded.

## Auto-mode classifier

The classifier reads `autoMode` from user settings, managed settings, and the `--settings` flag, never from a project `.claude/settings.json`, so this fragment holds all of the persistent configuration. Under the server-side review these sessions use, sandboxed and read-only commands also wait for the classifier and can be denied.

- `autoMode.environment` carries the machine-wide trust and sensitivity facts the auto-mode classifier needs, not repo-specific ones: the envchain credential store and its legitimate use, so a credential mention is not read as exploration, and the non-public scope, so delivering task material inside it is not read as egress. By default the classifier trusts only the working repository and its remotes and treats any other destination as a potential exfiltration target, so the scope entry restates that scope's predicate instead of naming accounts or services; a destination the predicate excludes stays outside the scope, and the authority rules own the disclosure judgment. Entries use the `**Slot**: value` form, and the list starts with `$defaults` so the built-in entries stay; a custom slot entry sits beside the built-in one of the same name rather than replacing it.
- `autoMode.allow` carries one custom entry, for local Git work. Plain status and history reads were denied as `Safety Bypass Flag` after an earlier bypass attempt in the same session, and a local tag was denied as a publication. A cross-repository local commit denied as a shared-resource change was an unsandboxed retry after the sandbox refused the write, which the entry excludes by leaving Git commands that carry the sandbox-bypass flag to the other rules, a wording that keeps plain `git`, which the sandbox exempts, inside the entry; that case needs the repository added with `/add-dir`, after which sandboxed `git -C` commits there with no path form named in the entry, so the entry names none. The entry is prose rather than `permissions.allow` prefixes because a prefix cannot express "read-only", and each subcommand would need separate rules for its plain and `-C <dir>` forms. It lists the covered operations exhaustively and clears the operation, not its content: allow entries override soft-deny rules, and several of those judge a commit's content, such as credential leakage and code that leaks when run, so the entry itself keeps every content rule in force and excludes discarding uncommitted work, pushes, published tags, and rewrites of pushed commits. It does not name amending: if the classifier reads an amend of an unpushed commit as committing, the built-in hold on amending a commit that predates the session no longer applies, and the `commit` skill's authorization rule for amend and fixup is the remaining guard. A fresh-fixture ablation on 2026-09-30 reproduced none of those denials without the entry, probably because they depended on context from long sessions, so the entry rests on the recorded denials as an exception to the reproducer rule below; in the same ablation, discarding uncommitted work stayed denied with the entry. The terminal-state-loss rules did not trigger for local temp-path operations, so they have no entry.
- Add an `autoMode.allow` entry only with a reproducer where the classifier denies without it. Keep `$defaults` first so every other built-in rule remains in force, and keep incident nouns and environment-specific identifiers (accounts, organizations, hosts, paths, the operating system) out of any entry, so it describes a kind of action rather than one environment that would need a new entry for each account; the tool an entry governs may be named.

## Sandbox

- Treat `excludedCommands` entries as deliberate command shapes, not universal wrapper-aware policies. Matching runs per segment, splitting on `&&`, `||`, `|`, `;`, `&`, and a newline, and the invocation is exempt only when every segment reduces to an excluded command with nothing but its own arguments, apart from a file-descriptor duplication such as `2>&1` and the stripped prefixes named below; a command substitution or heredoc sandboxes the invocation even in an argument position. An inline assignment before the command name, and any other non-exempt command in the call, keeps the whole invocation sandboxed, unless the CLI strips the assignment name as inert (such as `TERM`, `LANG`, or `NODE_ENV`). A bare `env` or `time` prefix is stripped before matching and keeps the exemption, but an `env` prefix whose value is not inert, such as `env PROBE=1`, does not. Git options that select another repository or configuration, such as `-C`, `-c`, `--git-dir`, and `--work-tree`, are rejected by a built-in check before any pattern is compared, so no entry form such as `git *` can exempt them; `git --no-pager` stays exempt. A socket-based tool such as `herdr` then fails with `Operation not permitted` rather than a recognizable permission error, and a `2>/dev/null` hides that message while the call still fails. Do not broaden a matcher without an observed failure.
- Keep `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`: the Claude global instructions tell agents that a `cd` does not carry over to the next Bash call, so a plain excluded `git` always acts on the session's working directory; removing the variable makes that sentence wrong.
- Extra write paths are locations that sandboxed work writes whatever project the session started in: development tool caches and stores, agent state, tool configuration and command entrypoints, and the shared worktree root. A repository outside the working directory is specific to a task, so the session adds it with `/add-dir` instead of listing it here. `~/.codex` serves sandboxed tools that manage Codex state (e.g. `gh skill update --agent codex --scope user`); codex itself runs excluded and no longer needs it. `~/.claude` and `~/.pi` let sandboxed commands maintain agent session stores, such as rewriting a Pi session header and renaming its `~/.pi/agent/sessions` directory after a project moves (the header write was denied on 2026-09-28); both were added by explicit user decision, as were `~/.config` and `~/.local/bin`, which hold tool configuration and command entrypoints. Claude Code's built-in write-deny paths under `~/.claude` (`settings.json`, `projects`, `hooks`, and similar) stay denied inside the allowed tree. Reads of credential files such as `~/.pi/agent/auth.json` are covered by agent-guard's `**/auth.json*`, not by the sandbox. `~/.oracle` exists for sandboxed parents of oracle such as the skill-validator smoke, whose oracle dry-run chmods `~/.oracle/sessions`; direct `oracle` commands run excluded and never needed it. Sandboxed writes to `~/.codex/config.toml` are a side effect of this entry; the file stays chezmoi-managed, so treat unexplained drift there as suspect. `~/Code/worktrees` is where the shared execution-host instructions put every worktree that outlives its task, so any session may create one there or return to one; without the entry, a sandboxed `git worktree add` into it and every sandboxed write inside such a worktree from a session started elsewhere fail with `Operation not permitted`. If those instructions name another directory, move this entry with them. Add a path only after an observed sandbox denial, and do not widen access to a whole home or source tree. `~/.gnupg/trustdb.gpg` is the only writable path under `~/.gnupg`, because sandboxed OpenPGP verification hung without it: gpg opens the trust database read-write and falls back to read-only only on `EACCES` or `EROFS`, Seatbelt refuses the write with `EPERM`, and with keyboxd in use the resulting fatal error deadlocks gpg while it exits. The cost is that any sandboxed command can rewrite ownertrust, which decides what `%G?` reports; keep the rest of `~/.gnupg`, including `gpg.conf`, read-only. A trust check also needs a lock file beside the database, so after a key import or ownertrust change the first verification that runs the pending check still hangs in the sandbox; any trust-using gpg call outside the sandbox clears it. Do not cover that window with `no-auto-check-trustdb`: the option is global, so outside the sandbox the trust database would never be refreshed and a never-checked one leaves the user's own key `[unknown]`. Remove the entry once GnuPG opens a write-denied trust database read-only.
- `denyRead` covers `~/.ssh` as a directory and `allowRead` reopens the same files the hook allows. `allowRead` accepts `*.pub` and `config.*` patterns, so keep the exceptions as patterns rather than key names; re-test pattern support with an isolated `--settings` file, because merged user settings mask a removal. `Read` deny rules also feed the sandbox, so a `Read(~/.ssh/...)` deny would block public keys inside the sandbox as well.
- Keep the rendered `getconf DARWIN_USER_TEMP_DIR` entry in `sandbox.filesystem.allowWrite`: macOS `mktemp` creates files in that per-user directory unless given `-p` or an explicit template path, so bare, `-d`, and `-t` calls ignore the sandbox's `TMPDIR`, and Claude's built-in allowlist omits the directory because [sandbox-runtime#182](https://github.com/anthropics/sandbox-runtime/pull/182) dropped the grant on the premise that `TMPDIR` suffices. Without the entry those calls fail with `Operation not permitted` in repository scripts and third-party tools alike, and agents retried them unsandboxed, so do not trade the entry for rewriting callers. Remove it only once Claude's sandbox grants that directory again, re-tested with an isolated `CLAUDE_CONFIG_DIR`, because merged user settings make an in-place removal test false-pass. Keep the exact rendered `T/` path rather than a glob that spans every user's `T/` or a `/var/folders` ancestor, which would also reopen the `C/` and `0/` siblings that change closed.
- Add allowed domains only after observed sandbox traffic: every entry widens egress for all sandboxed commands, while excluded commands never consult the list. A `*.host` entry matches subdomains at any depth but not the bare `host`, and a bare `host` entry does not match its subdomains, so list both when both are needed (probed 2026-09-29 against `*.claude.com`, `*.githubusercontent.com`, and `context7.com`). After the private hosts rendered from chezmoi data, order entries by registrable domain, a bare host before its wildcard, so each such pair stays adjacent; sorting the raw strings would gather every wildcard at the top. Keep `network.strictAllowlist` unset so a novel host prompts instead of failing deterministically; promote repeatedly approved hosts from runtime-owned state into `allowedDomains`. The setting is OR-merged, so another managed scope can still force strict mode.
- `allowUnixSockets` permits the gpg-agent and keyboxd sockets (private key and public-key lookup) plus the gpg-agent SSH socket. A `git` invocation runs sandboxed whenever the matcher above rejects its segment, so these serve sandboxed `gpg`, `ssh`, and git, including every `git -C` call, git sharing a call with a non-exempt command, and git under a sandboxed parent such as `gh`, `glab`, or a hook script. Without the keyboxd entry a sandboxed `gpg` reports `no keyboxd running in this session` while the daemon is running. The `/private/tmp/claude-<uid>` entry is the sandbox's own `TMPDIR`: every sandboxed Cargo build through mbx binds its cache session socket in a randomly named directory there, and without the entry the bind fails with `Operation not permitted` and each build prints a warning before falling back to FIFOs. Entries match as path prefixes for both bind and connect, so this directory is the narrowest stable entry; follow it if Claude Code moves the sandbox `TMPDIR`. `allowLocalBinding=true` emits three seatbelt rules, not one: bind and inbound on any local port, plus outbound to `localhost:*`. Sandboxed clients of a local server therefore depend on this same entry, so do not narrow it to the server side. `com.apple.trustd.agent` supports macOS certificate verification for Go-based CLIs; it is absent from the fixed built-in mach-lookup list, so this explicit entry is the only thing granting it short of `enableWeakerNetworkIsolation`, which the sandbox schema itself labels a security reduction. Add entries only after an observed failure.
- Keep `NODE_USE_ENV_PROXY=1`: the sandbox proxies egress, and Node's `fetch` ignores `HTTPS_PROXY` without it, so a sandboxed Node CLI fails with `fetch failed` even when its host is in `allowedDomains`; the flag is inert when `HTTPS_PROXY` is unset, so excluded commands are unaffected. The context7 skill's `ctx7` calls are the observed case. Remove the flag only after a cleanly restarted session runs a sandboxed Node CLI that uses `fetch` without it and succeeds.

## Models, context, and statusline

- Keep the aliases pinned: on the Vertex provider that gateway mode runs as, the built-in alias table points `sonnet` at `claude-sonnet-4-5` and `haiku` at `claude-haiku-4-5`, while `opus` and `fable` already match first-party. A pin outranks that table (probed 2026-10-08: `--model sonnet` through the gateway resolves to the pinned `claude-sonnet-5-5`, not to `claude-sonnet-4-5`), and it also stops a CLI upgrade from advancing the alias, so re-check the pins whenever a new model generation ships.
- Pin the four models by their exact IDs: `claude-fable-5-1`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`. The exact IDs matter because the gateway's clearance rules match them exactly, and that list is policy rather than deployment capability. The `[1m]` suffix is redundant because these models are natively 1M, so the client budgets 1M on both routes without it (probed 2026-10-08: bare `claude-opus-5-5`, `claude-sonnet-5-5` and `claude-fable-5-1` each report a 1000000-token window through the gateway). Keep the model IDs in the variables rather than at delegation call sites, whose model slots accept only the bare `opus`, `sonnet`, `haiku`, and `fable` aliases.
- `autoCompactWindow` is a compaction threshold, not evidence of the active model's context size. Verify the effective budget from `modelUsage[].contextWindow` in `claude -p --output-format json`, which resolves the window through the same function as the statusline and auto-compact, or from the `context_window.context_window_size` that Claude Code passes to the statusline; the picker's 1M label is not a window measurement, so confirm the number with one of those two sources.
- Leave flag-gated settings unset: `precomputeCompactionEnabled` and `autoDreamEnabled` both sit behind a server-side flag (`tengu_sepia_moth`, `tengu_onyx_plover`) that `DISABLE_TELEMETRY=1` stops fetching, so the client returns before reading either setting, and `precomputeCompactionEnabled` already defaults to true. Check the flag check before adding such a setting: one that only overrides a server-side default cannot change anything here.
- `dot_claude/scripts/executable_statusline.sh` owns its compact-window parser and denominator calculation. Update and test both when changing `autoCompactWindow` or adding support for another compact override.

## Integrations

- `CLAUDE_CODE_ENABLE_CFC=0` explicitly disables Claude in Chrome; it does not govern the separately permitted `chrome-devtools` MCP tools. Keep the explicit false value as a guard: when it is unset the client falls back to the `claudeInChromeDefaultEnabled` key in `~/.claude.json`, and only with neither present is Claude in Chrome off. Do not add that key to `modify_dot_claude.json`; the environment variable already outranks it.
- Keep `CLAUDE_CODE_DISABLE_CRON=1` with the bare `ScheduleWakeup` deny while local scheduling is retired. The environment variable removes `/loop` and the Cron tools, but the client still registers `ScheduleWakeup` eagerly. Cloud Routines are account-owned and unaffected. Remove the deny only after a cleanly restarted session and a resumed session, both with the environment flag enabled, cannot create, retain, or execute a scheduled wakeup through any exposed scheduling surface.
- `disableClaudeAiConnectors=true` is the source of truth for blocking auto-fetched claude.ai connectors; explicitly configured MCP servers remain available.
- `disableBundledSkills=true` keeps the repository-managed skill registry authoritative. Keep the separate `disableWorkflows` setting unset because `ultracode` depends on dynamic workflows.
- Keep `ENABLE_TOOL_SEARCH=1` as a guard, not as the switch: MCP tool deferral is already on in the subscription and Vertex-gateway modes because the client's mode selection returns `tst` with or without it, and the variable only lifts the block on a first-party session pointed at a non-Anthropic `ANTHROPIC_BASE_URL`. Re-test after gateway changes because the gateway must preserve `tool_reference` blocks that the default mode already sends.
- The `SessionStart` entry registers a hook owned by `herdr integration install claude`; see [Herdr integrations](../../.github/CONCEPTS.md#herdr-integrations). Keep the installer's whole entry, matcher, `bash '<absolute path>' session` command, and timeout, because the installer recognizes only that exact entry: with the repository's usual `~/.claude/hooks/...` command form a reinstall appends a duplicate, and any other difference makes every apply revert the entry the installer last wrote while `herdr integration status` still reports `current`, since it checks only the hook script's version. After a Herdr upgrade reruns the installer, a changed entry shows in `chezmoi status --exclude=encrypted ~/.claude/settings.json`; copy it from the live file.

## Worktrees

- `worktree.baseRef` stays unset (default `fresh`), so new worktrees branch from `origin/<default-branch>` instead of carrying local HEAD state.
