# Claude Code settings

This is not a settings reference. Keep only repository-specific decisions that cannot be recovered from the managed configuration, its owning code, or the [environment variable](https://code.claude.com/docs/en/env-vars), [settings](https://code.claude.com/docs/en/settings), and [sandbox](https://code.claude.com/docs/en/sandboxing) references.

Revalidate runtime-dependent evidence after upgrades.

## Ownership

Keep `~/.claude/settings.json` and `~/.claude.json` partially managed per the [configuration ownership boundary](../../.github/CONCEPTS.md#configuration-ownership), so keys source does not declare, which Claude Code writes at runtime, survive chezmoi applies. Do not replace their modifiers with complete templates; `chezmoi re-add` cannot reconcile these targets.

Each top-level key in `~/.claude/settings.json` has one of three roles:

- Managed: declared in `.chezmoitemplates/claude/settings.json`. Every apply overwrites the live value, so a change made inside Claude Code lasts only until the next apply. This is the default for any key source sets.
- Seed: declared in `$seeds` in `dot_claude/modify_private_settings.json`. Apply writes it only when the key is missing from the live file, and never touches it afterwards.
- Undeclared: in neither. Apply leaves the live value as Claude Code wrote it. Removing a key from the fragment moves it here without deleting its live value.

Seed a key only when routine use changes it so often that restoring it on every apply would undo that use. Only `model`, switched through `/model`, meets that bar; the seed still gives a new machine the intended starting value, which leaving it undeclared would not. Seed `model` as the `opus` alias rather than a model ID: a seed is written once, so an ID would freeze each machine on the generation current at its first apply, while the alias follows the Opus pin. Being changeable inside Claude Code is not the criterion: many managed keys, such as `permissions`, which `/permissions` edits, change in a session and stay managed, so make the change durable in the fragment.

Declare no effort setting. `/effort` saves each model's level under `modelSettings`, so keep that key undeclared: a managed subtree would erase the saved levels on every apply. A top-level `effortLevel` cannot stand in as a seed because Opus 5.5 ignores it, so a new machine starts Opus 5.5 at `medium` until `/effort` saves a level. Keep `CLAUDE_CODE_EFFORT_LEVEL` unset: it overrides every session's effort, and `/effort` then reports that its change was not applied.

`~/.claude.json` has no seeds. `modify_dot_claude.json` overlays its declared keys and replaces each source-declared MCP server whole, so removed transport fields disappear; undeclared servers and all other state stay intact.

## Session retention and unattended runs

- `cleanupPeriodDays=99999` intentionally retains transcripts for a practically indefinite period.
- `CLAUDE_CODE_RETRY_WATCHDOG=1` keeps unattended sessions waiting through retryable capacity errors. Keep `fallbackModel` unset while the watchdog is on: the watchdog exists to wait for the requested model, while a fallback would silently downgrade the runs it protects.

## Privacy and feature delivery

`DISABLE_TELEMETRY=1` also disables the client that evaluates server-side feature flags, and first-party event logging shares that gate, so no setting keeps flags while dropping events. Every gated feature therefore stays at its default, and each one wanted here needs its own explicit opt-in. Leave `CLAUDE_CODE_GB_DISK_CACHE_WHEN_TELEMETRY_OFF` unset: it only makes an existing flag cache in `~/.claude.json` readable while telemetry is off, and only sessions where the flag client runs write that cache, so on a machine that always has telemetry off it has nothing to read.

`syncClaudeAiSkills=false` and `syncClaudeAiPlugins=false` guard against a session that re-enables flag evaluation: account sync is switched on server-side by flags, and with them the flag would pull claude.ai skills into context and the repository-managed registry would stop being the only source.

Both fork mode and agent teams are intentionally enabled here: `CLAUDE_CODE_FORK_SUBAGENT=1` extends fork mode, already on by default in interactive sessions, to `claude -p` and the Agent SDK, and `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` turns on agent teams, which are off by default.

Do not consolidate the separate privacy controls into `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`; it would also disable automatic updates.

## Permission rules

Claude Code resolves an action against `permissions` rules before the auto-mode classifier sees it: a deny match blocks first, and an allow match skips classifier review, with documented exceptions such as writes to protected paths, commands that carry per-command allowed domains, and shell commands in a session with `autoMode.classifyAllShell`. `sandbox.excludedCommands` decides only where a command runs, not whether it may run, so an excluded command without an allow rule still goes to the classifier; do not mirror one list into the other.

- `Read`, `Edit`, and `Write` stay broadly allowed for routine file work. Classify a new credential path in the shared [agent guard](../../.github/CONCEPTS.md#agent-guard) package first: it checks the agent's own `Bash` and `Read|Edit|Write|Grep` calls in every runtime and resolves the paths a shell command reads. Add a `Read` or `Edit` deny here only for what the guard cannot reach: Claude merges those rules into the sandbox's `denyRead` and `denyWrite`, which hold every process a sandboxed command starts, so deny reading a credential file that no sandboxed tool needs to read (npm reads `~/.npmrc`, so it has only an `Edit` deny) and deny editing one that a sandboxed command could otherwise write. Put a credential directory in `sandbox.filesystem.denyRead` instead of a `Read(<dir>/**)` deny: when a command reads a relative file after a `cd` whose target Claude cannot resolve, such as a glob, Claude denies it if any `Read` deny could match that file, and a directory pattern matches every file name, while `denyRead` blocks the same sandboxed reads without entering that check. Add no `Bash(*name*)` deny: Claude matches it against the whole command text, so it blocks commands that only mention the name in a search term or a prompt, while a glob such as `~/.np*rc` reads the file past it. `~/.ssh` is the exception: the guard allows public keys, client config, `allowed_signers`, and `known_hosts` inside an otherwise private directory, which a deny glob cannot express, so do not add `~/.ssh` deny rules back. Grep permits explicit public files; directory searches covering private SSH material must be narrowed. Do not use glob rewriting to grant access: composing public reinclusions with the caller's filter changes search scope.
- Keep bare `Bash`, `PowerShell`, `Agent`, `Monitor`, and wildcarded interpreters, shells, or package-manager `run` commands out of `permissions.allow`: `auto` mode strips them before rule matching.
- `Bash(herdr:*)` and `Bash(oracle:*)` stay globally allowed because their panes or sessions can continue after the invoking Skill's turn, when frontmatter preapproval no longer applies. `Bash(snow:*)` stays globally allowed for the standing direct-command and native-SSO execution path owned by [Snowflake CLI execution](../../.github/CONCEPTS.md#snowflake-cli-execution). Their sandbox exclusions remain separately necessary for Herdr control, Oracle browser control, and native Snowflake SSO.
- `Bash(codex:*)` and `Bash(pi:*)` stay globally allowed by explicit user decision: agents choose their own flags for each consultant run, such as an approval-disabling `-c 'approval_policy="never"'` that the managed Codex defaults do not need, and the classifier denies such a run as `Create Unsafe Agents` from the command text alone. A global instruction against each flag would not cover the next one, so the rules skip classifier review for these commands, including `codex`, which also runs outside the sandbox.
- Other host CLIs get no global allow rule. Git and other same-turn commands keep their narrower Skill grants unless a current-version reproducer shows Claude denying the matching grant, and `chezmoi` and `docker` stay on the classifier path although they are sandbox-excluded.

## Auto-mode classifier

The classifier reads `autoMode` from user settings, managed settings, and the `--settings` flag, never from a project `.claude/settings.json`, so this fragment holds all of the persistent configuration. Under the server-side review these sessions use, sandboxed and read-only commands also wait for the classifier and can be denied.

- `autoMode.environment` carries the machine-wide trust and sensitivity facts the auto-mode classifier needs, not repo-specific ones: the envchain credential store and its legitimate use, so a credential mention is not read as exploration, and the non-public scope, so delivering task material inside it is not read as egress. By default the classifier trusts only the working repository and its remotes and treats any other destination as a potential exfiltration target, so the scope entry restates that scope's predicate instead of naming accounts or services; a destination the predicate excludes stays outside the scope, and the authority rules own the disclosure judgment. Entries use the `**Slot**: value` form, and the list starts with `$defaults` so the built-in entries stay; a custom slot entry sits beside the built-in one of the same name rather than replacing it.
- `autoMode` declares no `allow` entries, so the built-in allow rules apply as shipped, and steps of the user's task that the classifier would deny are left to `preallow@entwining-mods` (below), which judges each call against the user's own words before the classifier sees it. Allow entries cannot read those words: in replays, an entry for local Git work and one for merges the user asked for each cleared only part of its denial class, and entries restating the authorization standard moved denials in both directions without raising the allow rate. Add an entry only for a denial that preallow leaves to the classifier and should not, with a reproducer where the classifier denies without the entry and allows with it in a replay that loads the global instructions; keep `$defaults` first and accounts, hosts, paths, and other environment-specific identifiers out of it.

## Sandbox

- Treat `excludedCommands` entries as deliberate command shapes, not universal wrapper-aware policies. Matching runs per segment, splitting on `&&`, `||`, `|`, `;`, `&`, and a newline, and the invocation is exempt only when every segment reduces to an excluded command with nothing but its own arguments, apart from a file-descriptor duplication such as `2>&1` and the stripped prefixes named below; a command substitution or heredoc sandboxes the invocation even in an argument position. An inline assignment before the command name, and any other non-exempt command in the call, keeps the whole invocation sandboxed, unless the CLI strips the assignment name as inert (such as `TERM`, `LANG`, or `NODE_ENV`). A bare `env` or `time` prefix is stripped before matching and keeps the exemption, but an `env` prefix whose value is not inert, such as `env PROBE=1`, does not. Git options that select another repository or configuration, such as `-C`, `-c`, `--git-dir`, and `--work-tree`, are rejected by a built-in check before any pattern is compared, so no entry form such as `git *` can exempt them; `git --no-pager` stays exempt. A socket-based tool such as `herdr` then fails with `Operation not permitted` rather than a recognizable permission error, and a `2>/dev/null` hides that message while the call still fails. Do not broaden a matcher without an observed failure.
- `ps` and `pgrep` are excluded because Claude's Seatbelt profile allows `process-info*` only for processes inside the same sandbox and no setting widens it, so a sandboxed process listing fails with `operation not permitted: ps` or `pgrep: Cannot get process list`. Both only read process metadata and have no allow rule, so the classifier still reviews each call. A pipeline such as `ps … | grep` stays sandboxed and fails, while `pgrep -lf PATTERN` filters on its own. Remove both entries once a sandboxed `ps -ax` lists processes outside the sandbox.
- Keep `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`: the Claude global instructions tell agents that a `cd` does not carry over to the next Bash call, so a plain excluded `git` always acts on the session's working directory; removing the variable makes that sentence wrong.
- Extra write paths in `sandbox.filesystem.allowWrite` are locations that sandboxed work writes whatever project the session started in: development tool caches and stores, agent state, tool configuration and command entrypoints, and the shared worktree root. A repository outside the working directory is specific to a task, so the session adds it with `/add-dir` instead of listing it here. Add a path only after an observed sandbox denial, and do not widen access to a whole home or source tree.
  - `~/.codex` serves sandboxed tools that manage Codex state (e.g. `gh skill update --agent codex --scope user`); codex itself runs excluded and does not need it. Sandboxed writes to `~/.codex/config.toml` are a side effect of this entry; the file stays chezmoi-managed, so treat unexplained drift there as suspect.
  - `~/.claude` and `~/.pi` let sandboxed commands maintain agent session stores, such as rewriting a Pi session header and renaming its `~/.pi/agent/sessions` directory after a project moves; both were added by explicit user decision, as were `~/.config` and `~/.local/bin`, which hold tool configuration and command entrypoints. Claude Code's built-in write-deny paths under `~/.claude` (`settings.json`, `projects`, `hooks`, and similar) stay denied inside the allowed tree. Reads of credential files such as `~/.pi/agent/auth.json` are covered by agent-guard's `**/auth.json*`, not by the sandbox.
  - `~/Code/worktrees` is where the shared execution-host instructions put every worktree that outlives its task, so any session may create one there or return to one; without the entry, a sandboxed `git worktree add` into it and every sandboxed write inside such a worktree from a session started elsewhere fail with `Operation not permitted`. If those instructions name another directory, move this entry with them.
  - `~/.gnupg/trustdb.gpg` is the only writable path under `~/.gnupg`, because sandboxed OpenPGP verification hung without it: gpg opens the trust database read-write and falls back to read-only only on `EACCES` or `EROFS`, Seatbelt refuses the write with `EPERM`, and with keyboxd in use the resulting fatal error deadlocks gpg while it exits. The cost is that any sandboxed command can rewrite ownertrust, which decides what `%G?` reports; keep the rest of `~/.gnupg`, including `gpg.conf`, read-only. A trust check also needs a lock file beside the database, so after a key import or ownertrust change the first verification that runs the pending check still hangs in the sandbox; any trust-using gpg call outside the sandbox clears it. Do not cover that window with `no-auto-check-trustdb`: the option is global, so outside the sandbox the trust database would never be refreshed and a never-checked one leaves the user's own key `[unknown]`. Remove the entry once GnuPG opens a write-denied trust database read-only.
  - Keep the rendered `getconf DARWIN_USER_TEMP_DIR` entry in `sandbox.filesystem.allowWrite`: macOS `mktemp` creates files in that per-user directory unless given `-p` or an explicit template path, so bare, `-d`, and `-t` calls ignore the sandbox's `TMPDIR`, and Claude's built-in allowlist omits the directory because [sandbox-runtime#182](https://github.com/anthropics/sandbox-runtime/pull/182) dropped the grant on the premise that `TMPDIR` suffices. Without the entry those calls fail with `Operation not permitted` in repository scripts and third-party tools alike, and agents retried them unsandboxed, so do not trade the entry for rewriting callers. Remove it only once Claude's sandbox grants that directory again, re-tested with an isolated `CLAUDE_CONFIG_DIR`, because merged user settings make an in-place removal test false-pass. Keep the exact rendered `T/` path rather than a glob that spans every user's `T/` or a `/var/folders` ancestor, which would also reopen the `C/` and `0/` siblings that change closed.
  - `/private/tmp/diff.*` serves macOS `/usr/bin/diff`, which copies pipe or process-substitution input, as in `cmd | diff - file` or `diff <(a) <(b)`, to a file it names under a hardcoded `/tmp`, ignoring `TMPDIR`; without the entry those calls fail with `Operation not permitted`. The glob admits only those files, not the rest of `/tmp`. Remove it once macOS `diff` honors `TMPDIR` or Claude's sandbox grants `/tmp` writes.
- `denyRead` covers `~/.ssh` as a directory and `allowRead` reopens the same files the hook allows. `allowRead` accepts `*.pub` and `config.*` patterns, so keep the exceptions as patterns rather than key names; re-test pattern support with an isolated `--settings` file, because merged user settings mask a removal. `Read` deny rules also feed the sandbox, so a `Read(~/.ssh/...)` deny would block public keys inside the sandbox as well.
- Add allowed domains only after observed sandbox traffic: every entry widens egress for all sandboxed commands, while excluded commands never consult the list. A `*.host` entry matches subdomains at any depth but not the bare `host`, and a bare `host` entry does not match its subdomains, so list both when both are needed. After the private hosts rendered from chezmoi data, order entries by registrable domain, a bare host before its wildcard, so each such pair stays adjacent; sorting the raw strings would gather every wildcard at the top. Keep `network.strictAllowlist` unset so a novel host prompts instead of failing deterministically; promote repeatedly approved hosts from runtime-owned state into `allowedDomains`. The setting is OR-merged, so another managed scope can still force strict mode.
- `allowUnixSockets` permits the gpg-agent and keyboxd sockets (private key and public-key lookup) plus the gpg-agent SSH socket. A `git` invocation runs sandboxed whenever the matcher above rejects its segment, so these serve sandboxed `gpg`, `ssh`, and git, including every `git -C` call, git sharing a call with a non-exempt command, and git under a sandboxed parent such as `gh`, `glab`, or a hook script. Without the keyboxd entry a sandboxed `gpg` reports `no keyboxd running in this session` while the daemon is running. The `/private/tmp/claude-<uid>` entry is the sandbox's own `TMPDIR`: every sandboxed Cargo build through mbx binds its cache session socket in a randomly named directory there, and without the entry the bind fails with `Operation not permitted` and each build prints a warning before falling back to FIFOs. Entries match as path prefixes for both bind and connect, so this directory is the narrowest stable entry; follow it if Claude Code moves the sandbox `TMPDIR`. Add entries only after an observed failure.
- `allowLocalBinding=true` emits three seatbelt rules, not one: bind and inbound on any local port, plus outbound to `localhost:*`. Sandboxed clients of a local server therefore depend on this same entry, so do not narrow it to the server side.
- The `com.apple.trustd.agent` entry in `allowMachLookup` supports macOS certificate verification for Go-based CLIs; it is absent from the fixed built-in mach-lookup list, so this explicit entry is the only thing granting it short of `enableWeakerNetworkIsolation`, which the sandbox schema itself labels a security reduction. Add entries only after an observed failure.
- Keep `NODE_USE_ENV_PROXY=1`: the sandbox proxies egress, and Node's `fetch` ignores `HTTPS_PROXY` without it, so a sandboxed Node CLI fails with `fetch failed` even when its host is in `allowedDomains`; the flag is inert when `HTTPS_PROXY` is unset, so excluded commands are unaffected. The context7 skill's `ctx7` calls are the observed case. Remove the flag only after a cleanly restarted session runs a sandboxed Node CLI that uses `fetch` without it and succeeds.

## Models, context, and statusline

- Keep the aliases pinned: on the Vertex provider that gateway mode runs as, the built-in alias table points `sonnet` at `claude-sonnet-4-5` and `haiku` at `claude-haiku-4-5`, while `opus` and `fable` already match first-party. A pin outranks that table, and it also stops a CLI upgrade from advancing the alias, so re-check the pins whenever a new model generation ships.
- Pin each alias to an exact model ID without a `[1m]` suffix. The exact IDs matter because the gateway's clearance rules match them exactly, and that list is policy rather than deployment capability. The suffix is redundant because the pinned models are natively 1M, so the client budgets 1M on both routes without it. Keep the model IDs in the variables rather than at delegation call sites, whose model slots accept only the bare `opus`, `sonnet`, `haiku`, and `fable` aliases.
- `autoCompactWindow` is the compaction threshold, 350K for every model, and Claude Code compacts 33K below it; unset, a natively 1M model compacts near 1M. The value trades the Claude weekly limit against compactions: in a cost replay of this machine's Opus 5.5 history, 1M cost 1.2 times 400K, and each 50K step below 400K saved about 3% while the added compactions grew faster. Raise it if compaction visibly hurts long tasks or the weekly limit stops binding. `/autocompact` saves a value for the current model under `modelSettings` that outranks this one, even as `auto`, which means the model's own default; delete that entry to return the model to 350K.
- Measure the active model's context window from `modelUsage[].contextWindow` in `claude -p --output-format json`, which resolves the window through the same function as the statusline and auto-compact, or from the `context_window.context_window_size` that Claude Code passes to the statusline. Neither `autoCompactWindow` nor the picker's 1M label is a window measurement.
- `promptCacheTtl: "1h"` keeps the main conversation's cache for an hour. Subscription sessions already default to that; the setting is for the Vertex gateway mode, which would otherwise use 5 minutes. Subagents, workflows, and helper requests stay at 5 minutes because their idle gaps rarely exceed that, so a 1h write premium would rarely pay for itself. Keep `ENABLE_PROMPT_CACHING_1H` unset: it sets the TTL of every request class without its own setting, so it would move those to 1h as well.
- Leave flag-gated settings unset: `precomputeCompactionEnabled` and `autoDreamEnabled` both sit behind a server-side flag (`tengu_sepia_moth`, `tengu_onyx_plover`) that `DISABLE_TELEMETRY=1` stops fetching, so the client returns before reading either setting, and `precomputeCompactionEnabled` already defaults to true. Check the flag check before adding such a setting: one that only overrides a server-side default cannot change anything here.
- `dot_claude/scripts/executable_statusline.sh` owns its compact-window parser and denominator calculation. Update and test both when changing `autoCompactWindow` or adding support for another compact override.

## Integrations

- `CLAUDE_CODE_ENABLE_CFC=0` explicitly disables Claude in Chrome; it does not govern the separately permitted `chrome-devtools` MCP tools. Keep the explicit false value as a guard: when it is unset the client falls back to the `claudeInChromeDefaultEnabled` key in `~/.claude.json`, and only with neither present is Claude in Chrome off. Do not add that key to `modify_dot_claude.json`; the environment variable already outranks it.
- Keep `CLAUDE_CODE_DISABLE_CRON=1` with the bare `ScheduleWakeup` deny while local scheduling is retired. The environment variable removes `/loop` and the Cron tools, but the client still registers `ScheduleWakeup` eagerly. Cloud Routines are account-owned and unaffected. Remove the deny only after a cleanly restarted session and a resumed session, both with the environment flag enabled, cannot create, retain, or execute a scheduled wakeup through any exposed scheduling surface.
- `disableClaudeAiConnectors=true` is the source of truth for blocking auto-fetched claude.ai connectors; explicitly configured MCP servers remain available.
- `disableBundledSkills=true` keeps the repository-managed skill registry authoritative. Keep the separate `disableWorkflows` setting unset because `ultracode` depends on dynamic workflows.
- Keep `ENABLE_TOOL_SEARCH=1` as a guard, not as the switch: MCP tool deferral is already on in the subscription and Vertex-gateway modes because the client's mode selection returns `tst` with or without it, and the variable only lifts the block on a first-party session pointed at a non-Anthropic `ANTHROPIC_BASE_URL`. Re-test after gateway changes because the gateway must preserve `tool_reference` blocks that the default mode already sends.
- `preallow@entwining-mods` comes from the user's own marketplace. In auto mode it asks a model judge about each call the classifier would see, allows a reversible step of the user's task or an effect the user's own words asked for, and leaves everything else to the classifier; its README says what it reads and leaves alone. Keep `pluginConfigs` undeclared: its `model` and `effort` settings default to the configuration its evaluation chose, and a managed value would override a per-machine choice on every apply.
- The `SessionStart` entry registers a hook owned by `herdr integration install claude`; see [Herdr integrations](../../.github/CONCEPTS.md#herdr-integrations). Keep the installer's whole entry, matcher, `bash '<absolute path>' session` command, and timeout, because the installer recognizes only that exact entry: with the repository's usual `~/.claude/hooks/...` command form a reinstall appends a duplicate, and any other difference makes every apply revert the entry the installer last wrote while `herdr integration status` still reports `current`, since it checks only the hook script's version. After a Herdr upgrade reruns the installer, a changed entry shows in `chezmoi status --exclude=encrypted ~/.claude/settings.json`; copy it from the live file.

## Worktrees

- `worktree.baseRef` stays unset (default `fresh`), so new worktrees branch from `origin/<default-branch>` instead of carrying local HEAD state.
