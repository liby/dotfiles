Dotfiles managed by [chezmoi](https://www.chezmoi.io/) from `~/.local/share/chezmoi` to `$HOME`. Standard source prefixes and template mechanics live in the [chezmoi reference](https://www.chezmoi.io/reference/); this file records only repository-specific workflows and traps.

## Workflow

- After editing `.chezmoi.toml.tmpl`, run `chezmoi init` to regenerate `~/.config/chezmoi/chezmoi.toml`; never edit that generated file directly.
- Edit `Brewfile` in source. It is ignored for deployment and consumed by a `run_onchange` script whose template hash retriggers on content changes.
- Number scripts independently within the `before`, unqualified update, and `after` phases using contiguous two-digit prefixes. Renumber a phase when inserting a script instead of reserving numeric gaps.
- On a fresh `chezmoi init`, `R` status for every `run_once` script is expected.
- Before committing, run `chezmoi status --exclude=encrypted`; plain `chezmoi status` generates encrypted target state and can expose decrypted content. For each changed non-secret target in scope, run `chezmoi diff <dest-path>`; never run bare `chezmoi diff`. Read `-` as destination-only and `+` as rendered-target-only. Re-add destination-only drift only when it belongs to the requested change; report unrelated drift without modifying it. When both destination and target changed, show the scoped diff.
- Use `chezmoi merge <dest-path>` only for an explicitly selected non-secret, non-`modify_` target; a templated target requires manual review to preserve template directives.
- Fold a follow-up change to the same logical unit into its existing unpushed commit (`git commit --amend` or fixup) instead of appending a commit per request; append-only committing turns one feature into a chain that later needs a history rewrite. Start a new commit only for a separate concern, a pushed base, or another author's commit.
- When retiring or replacing a managed path, verify the exact non-secret destination, then delete the obsolete source and the existing live destination in the same change. Never add `remove_` entries, compatibility readers, or other migration markers; handle any later residue through an explicit audit.
- For agent skill changes, run `ruby dot_agents/skills/scripts/validate-skills.rb --smoke`. Keep `CLI_SMOKE_COMMANDS` in sync only for skills whose instructions depend on current CLI behavior.

## Encrypted Files

Protect the plaintext boundary, not repository-declared ciphertext. Treat a tracked ciphertext source as an opaque artifact: agents may inspect its metadata and encryption marker and may stage, commit, rename, or delete it when project documentation or the user supplies the change intent. Do not read its body for semantic evidence, infer plaintext changes, or describe them in a commit message. If encryption is not established, stop before reading the body.

- Hand every operation that can expose or derive secret plaintext to the user, including add or re-encrypt from a real secret, decrypt, `chezmoi edit`, `chezmoi re-add`, and `chezmoi merge`. Never run `chezmoi merge` for any encrypted target.
- Add a non-secret encrypted file with `chezmoi add --encrypt <file>`. Edit encrypted non-secret content through `chezmoi edit <dest-path>` or edit its deployed plaintext and run `chezmoi re-add`; never edit an `encrypted_*.asc` source directly. Decryption requires a Yubikey.
- `.secrets/seed.asc` is secret-bearing, repository-only ciphertext for envchain namespaces. The user must edit it with `chezmoi edit-encrypted .secrets/seed.asc` and then run `chezmoi apply ~/.chezmoiscripts/04-seed-envchain.sh` to reseed the Keychain. Its plaintext is TOML with one top-level table per namespace and one environment variable per single-line string value; quote numeric and boolean-looking values too.

  ```toml
  [service]
  API_KEY = "replace-with-value"
  ```
- A ciphertext source may share a commit with related non-secret changes; it does not require a commit of its own. Whatever the commit shape, describe the ciphertext generically, such as `update encrypted zshenv`: metadata and user-supplied change classification may justify the commit, but describing inferred plaintext changes defeats the encryption boundary.

## Project Invariants

Keep only non-obvious, durable relationships that name the harmful "fix" they prevent; otherwise rewrite or delete them.

- **Supported platform**: This repository targets Apple Silicon macOS only. Use the `/opt/homebrew` prefix directly; do not add Intel `/usr/local` branches until a supported machine requires them.
- **Codex config ownership**: Manage `model`, `desktop.followUpQueueMode = "steer"`, explicit enablement for source-managed MCPs other than the Desktop-provided `node_repl`, and the portable `mcp_servers.node_repl` launch fields in source. Keep the bundled Computer Use plugin enabled, but leave the standalone `mcp_servers.computer-use` registration unmanaged so Desktop owns its legacy runtime state; per-app authorization also remains runtime-owned. Leave App-written `features.js_repl`, `mcp_servers.node_repl.enabled`, `mcp_servers.node_repl.env`, and `model_reasoning_effort` unmanaged so the modifier preserves those live write-backs; see [openai/codex#24387](https://github.com/openai/codex/issues/24387#issuecomment-4531286877).
- **Codex unattended approvals**: Keep `approval_policy = "on-request"`, `approvals_reviewer = "auto_review"`, and custom `default_permissions = "development"` together, and constrain `.chezmoitemplates/codex/requirements.toml` to that sole policy, reviewer, and permission profile. This prevents task loading from accepting the `never` / `user` replacement in [#33552](https://github.com/openai/codex/issues/33552) and intentionally removes the built-in modes, including Full Access. After an auto-review denial, state the exact action and risk and retry only after explicit user reapproval. Treat the task-reported tuple as authoritative. The installed 0.147 reviewer constraint is load-time only, so restart Desktop after changing it and verify live-update enforcement once [#37511](https://github.com/openai/codex/pull/37511) reaches Desktop.
- **Codex filesystem profile**: Keep `development` standalone with `:root = write`, zero denied-read entries, and exact read-only `.env` and `.env.local` entries under every workspace root. This avoids routine filesystem approvals while preserving `.env` write protection and letting matching Rules select execution outside the inner sandbox. Expose only `development`; do not mirror per-tool cache lists or add broad command allows. Filesystem capability does not authorize remote Git or secret-bearing chezmoi operations.
- **Codex credential storage**: Keep both `cli_auth_credentials_store` and `mcp_oauth_credentials_store` on explicit `keyring`; `auto` may silently fall back to plaintext files. Before activating this setting on a machine, a credential-safe status check using that exact store must confirm the existing login. Agents never migrate, rewrite, or delete the real store.
- **Snowflake CLI ownership**: Keep direct `snow` commands broadly approved and excluded from the inner sandbox so the installed Homebrew client retains one native-SSO execution identity. Codex Rules own both decisions for Codex; Claude's `permissions.allow` and `sandbox.excludedCommands` own approval and exclusion separately. The personal `snow` skill owns CLI behavior and same-task SSO handling; Snowflake RBAC owns server authorization. Do not narrow the permission to `snow sql -q` or restore workspace `uvx` runtimes.
- **Codex opaque client inputs**: Programs may consume credential and environment files through their normal interfaces: package managers may read `.npmrc`, SSH may use keys, and application code may load `.env`. Keep each workspace root's exact `.env` and `.env.local` read-only. Request normal filesystem expansion for a change or deletion only when the current user instruction explicitly asks for that effect.
- **Codex managed Bash guard**: Keep one zsh `PreToolUse` hook enabled from `.chezmoitemplates/codex/requirements.toml` under `~/.codex/managed-hooks`. It blocks common top-level direct-display and credential-extraction commands and rejects direct `claude` calls or `envchain ... claude` without `claude-gateway`. Treat it as a model-misuse guardrail, not child-process isolation or output redaction. Do not turn it into a general shell parser, client allowlist, secret broker, or authentication boundary, and do not describe it as complete enforcement.
- **Codex direct networking**: Keep `features.network_proxy = false` with `permissions.development.network.enabled = true`; this leaves public and local networking direct while the permission profile still enforces filesystem access. Add proxy-only `domains` and `allow_local_binding` only with managed proxy enforcement; see [openai/codex#33227](https://github.com/openai/codex/issues/33227).
- **GPG bootstrap order**: Keep the GPG agent and YubiKey public-key bootstrap after Brewfile installation but in the `before` phase. Encrypted targets are decrypted during file sync, so moving this owner to `after` deadlocks a fresh machine before its key can be fetched.
- **Homebrew autoupdate state**: The Brewfile installer recreates the exact daily update, upgrade, and cleanup LaunchAgent and verifies it in the user's `gui/$UID` launchd domain. Do not replace that check with `brew autoupdate status`: the command uses the caller's bootstrap namespace and can report `stopped` from another app while the periodic GUI agent is loaded.
- **Case-sensitive Code volume**: Derive the APFS container from the filesystem that stores `$HOME`, constrain the unique case-sensitive `Code` volume to that container, and own its persistent UUID mount through `vifs`. Refuse a non-empty or differently mounted `~/Code`; never automatically unmount a volume or restore first-container/human-output matching. This `run_once` provisions bootstrap state rather than reconciling later drift. Run `/usr/bin/python3 .github/tests/setup_case_sensitive_volume_test.py` after changes; Docker cannot validate APFS or Disk Arbitration, so fresh-Mac reboot acceptance remains manual.
- **Manual Logseq pin**: Keep Logseq outside `Brewfile` and Homebrew cask ownership. This machine intentionally uses a manually installed 0.10.15 because 2.x is incompatible; do not add or adopt the `logseq` cask.
- **Proto bootstrap ownership**: `Brewfile` owns the `proto` executable; the Node bootstrap owns only the Node.js and pnpm toolchains under `PROTO_HOME`. Do not restore proto's standalone installer or an ad hoc `brew install` path.
- **Flat skill registry**: the filesystem under `dot_agents/skills` is the only skill registry. Do not add index READMEs, manifests, or topical bucket folders: chezmoi mirrors source paths into `~/.agents/skills`, and Claude Code only scans the top level of a skills directory, so any non-ignored subfolder makes the skills inside it undiscoverable.
- **Pi config ownership**: Manage `~/.pi/agent/models.json` fully and `~/.pi/agent/settings.json` partially through its modify template: pi rewrites `defaultProvider` and `defaultModel` on every `/model` selection, so `defaultModel` stays seed-only and `defaultProvider` is enforced only while `rc-gateway` is the sole provider. The rest of `~/.pi/agent` (credentials, sessions, installed packages) is runtime-owned, so never `chezmoi add` that directory — adopting it would commit live credentials. Keep both managed source directories `private_` so apply preserves mode `0700` instead of exposing runtime-owned contents through `0755` directories. The gateway base URL comes from `.private.aiGatewayBaseUrl` and the API key resolves at runtime through the `pi` envchain namespace (`AI_GATEWAY_TOKEN` in `.secrets/seed.asc`), so the rendered file carries no secret.
- **Global developer tools**: `.github/dev-tools/package.json` declares exact global npm tool versions, and `.github/dev-tools/requirements.txt` declares Pyright. Renovate includes them in the repository-wide `All dependencies` group, and `validate-dev-tools.yml` gives a dev-tools-only PR a real status check. Do not restore file-scoped `ignoreTests`: on a mixed group it can become branch-level config and bypass unrelated checks. Their shared `run_onchange` installer reconciles each declaration independently, so retries skip versions that already match. Do not split the installer or update or prune entire npm and uv stores; unmanaged machine-local tools may coexist.
