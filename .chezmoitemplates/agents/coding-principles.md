## Coding Principles

Prefer one real code path. Follow the repository's pattern for the same case and reuse implementations from the codebase, its existing dependencies, or the standard library instead of duplicating a parser, matcher, or helper. Use direct names, types, and control flow for readability. A helper, wrapper, or abstraction needs a contract beyond making code look self-explanatory. Name values for what they identify and operations for what they guarantee. Before naming a new file, directory, identifier, or key, read the repository's names for its peers and match case, separator, word order, and prefixes. Introduce an abbreviation, or a prefix or path segment that only repeats the enclosing directory, module, or namespace, only if the repository or library uses it. Add env vars, config switches, caches, fallbacks, compatibility layers, or abstractions only for an existing caller, deployment environment, migration path, or documented external API behavior that needs them.

Keep every changed line within the root-cause scope Authority defines or the adjacent repairs below. Clean the orphans your own change created (imports, variables, functions made unreachable). A correction or review finding about one instance names a class: sweep the surface the task owns, including delegated work and its briefs, and fix every confirmed instance of that shape, whoever introduced it. During implementation, also fix a confirmed defect you encounter when the repair stays within an owner the task can change, is inexpensive, low-risk, and verifiable, and needs no decision only the user or another owner can make; keep it free of unrelated refactoring. Report a defect as "noticed but not fixed" only with the condition it fails, such as belonging to another owner or costing clearly more to repair than it harms; predating the task or lying outside the changed files is not such a condition. When such a defect blocks the fix, Authority applies. When two patterns in the codebase contradict, do not blend them: pick one (more recent or better tested), state why, and flag the other.

Before changing a config constant, business threshold, or risk parameter, locate its read sites and state the direction of effect, such as `larger = more aggressive`.

For incremental frontend changes, preserve design tokens, components, and responsive behavior. Add no unrequested features or decorative UI. Verify UI at a running URL or in a file preview. Start the app only if it takes no resource from an in-use instance. Disclose uninspected rendered UI in the final answer.

Each test protects a distinct behavior partition, regression, or interaction contract. Derive assertions from the contract so they reject a plausible violation and survive behavior-preserving changes. Reuse a regression check that covers a reproducible bug. When adding a regression check for a reproducible bug, show it rejects the fault before using its pass to validate the fix. Keep repository-required checks and report material unverified behavior.

A comment states the non-obvious reason at the owning boundary. Give a constraint or invalidation condition only if maintainers need it to tell when the reason expires. Omit restated operations, intermediate attempts, and speculative work. Put durable contracts in the owning documentation. Keep comparisons of current behavior with what it replaced out of comments and ordinary project docs. In comments and ordinary project docs, leave owner-controlled values (model name, version, count, date) unpinned unless that text owns the pin. Keep existing project docs (PRD, todo, changelog) consistent with actual changes. Plans list only work items, without time estimates.
