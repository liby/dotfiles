## Protected Inputs

The never-read set is material whose purpose is to hold secrets: credential stores and their contents, private keys, declared environment files, and repository-declared ciphertext. Classify by that purpose from governing contracts, credential stores, privileged capability, or in-scope operator or project declarations; names, appearance, scanner hits, storage primitives, and enforcement blocks do not classify material, and a path containing `env`, `secret`, or `token` is not by itself evidence of plaintext. Any other file the task concerns, such as source, configuration, logs, or data, is ordinary input even when it may embed a credential. When it is unclear whether something is a store rather than a file that may contain a value, resolve that through bounded non-value evidence or one focused question, never by testing the value.

Never read the never-read set. Wherever a secret value surfaces, whether in an ordinary file the task reads, command arguments, process lists, shell history, logs, or tool output, do not extract or repeat it: keep it out of chat, code, commands, logs, diffs, new files, commits, and anything sent elsewhere, locally, remotely, over SSH, or on deployment targets; refer to it by location and kind, and describe where the user can inspect or rotate it.

Treat repository-declared ciphertext as an opaque artifact. Once project instructions or an encryption marker establish that classification, inspect metadata freely, and stage, commit, rename, or delete it only when the user or project documentation supplies the change intent; describe it generically in commit messages, and never decrypt, render, infer, or quote its contents. Remote and discarding Git operations on it still follow Authority.

Personal API credentials live in the macOS Keychain under envchain namespaces named after the consuming tool or service (`envchain --list` enumerates them), not in the shell environment or dotfiles. Run consumers through `envchain <namespace> <command>`, comma-joining namespaces when a tool needs several; in ad-hoc commands, reference the variables inside a single-quoted `sh -c`. Values stay in the consuming client's namespace and expand only inside the wrapped process, not in a shell where they are empty. On a missing or invalid credential, tell the user to run `envchain --set <namespace> <VAR>` in their own terminal; never ask for or handle the raw value.

Never mutate a real credential store, including to repair a failing credential; steps that write a store are handed to the user, while a user-requested change to a non-store source setting can be made. Authorized clients retain their normal credential source without inspection, printing, suppression, redirection, or replacement; change that source only when requested, and remove safety-only workarounds once evidence resolves their concern.

Declared environment files are opaque client inputs. Changing or deleting an exact workspace `.env` or `.env.local` requires an explicit user request and the normal filesystem permission expansion. In mixed non-store files, edit unrelated fields only when protected values stay byte-identical in place and absent from model-visible output and diffs; otherwise hand the edit back.

New or changed lifecycle and build code is untrusted until that exact code is authorized to run with the credential source: disable it, use a credential-free phase, isolate it, or report the boundary. Credential probes use isolated homes and synthetic stores, and a claim about a live account needs credential-safe status evidence or stays `unverified`.
